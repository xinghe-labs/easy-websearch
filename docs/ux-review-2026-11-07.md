## 一、总体结论

**核心链路是通的**：`npx skills add xinghe-labs/easy-websearch` 一条命令装好、
免 key 立即可搜、中文源可达、fetch 正文质量好、doctor 自检清晰、JSON 结构对
agent 友好。但体验中发现了 **2 个 P0 问题、3 个 P1 问题**和若干改进建议，
其中 P0-1（未知 flag 静默变成搜索词）和 P0-2（Python 路径下 Bing 返回垃圾
结果而非失败）会直接让新用户得出"这 skill 不行"的第一印象。

## 三、问题清单

### P0 — 会直接破坏第一印象，建议尽快修

**P0-1：未知 flag 被静默当作搜索词**（node + python 双实现同样存在）
- 复现：`node scripts/search.mjs --help` → 把 "help" 当查询词搜索，返回剑桥词典
- 影响：用户打错 flag（`--lanng`、`-help`）会得到貌似正常的垃圾结果，毫无警告
- 建议：解析参数时校验 flag，未知 flag 报错并列出合法 flag；支持 `--help`/-h 打印用法

**P0-2：Python/urllib 路径下 Bing 降级为"垃圾结果"而非干净失败**
- 复现：同机同刻，node 查 "webgpu" 返回 MDN（正常）；python 查 "webgpu" 返回
  Google 首页广告 / 百度百科混凝土灌注 —— Bing 将 urllib 客户端识别为机器人，
  不拒绝请求而是塞不相关内容
- 影响：RRF 会把垃圾当正常结果输出，用户/agent 会引用完全不相关的来源，
  比"引擎失败"危害大得多
- 建议（任选或组合）：
  1. Python 端补全浏览器特征（完整 header 集、cookie jar、与 node 对齐）
  2. junk 信号检测：结果全部是首页/同一域名/与查询零词重叠时，标记引擎
     "suspect" 并软失败，让其他引擎接管
  3. 文档明示该风险与 `--engine bing` 的排障方法

### P1 — 明显影响体验

**P1-3：文本模式引擎状态走 stderr、结果走 stdout**
- 复现：`node search.mjs "q" 2>&1 | head` 时引擎块插在结果标题和 URL 中间
- 建议：文本模式把引擎状态也打 stdout（stderr 留给真正的诊断信息），或提供
  `--quiet` 只输出结果

**P1-4：引擎名写错时提示不友好**
- 复现：`--engine duckduckgo` → "No search engines available..."，不说可选值
- 建议：报错列出全部有效引擎名，并做近似匹配提示（"did you mean ddg?"）

**P1-5：冷却机制缺少文档出口**
- 现状：state 在 `$XDG_CACHE_HOME/easy-websearch/cooldowns.json`，README/SKILL.md
  均未提及；doctor 也不显示冷却状态；用户想"让 ddg 再试一次"找不到办法
- 建议：README 加"故障排查"小节（state 位置、删除即重置）；doctor 输出加一列
  冷却状态；考虑 `--clear-cooldown` 或复用 `--no-cooldown` 说明

### P2 — 建议与优化

- **P2-6**：`--days` 在 Bing 上静默忽略，可在引擎行标注 `days ignored`
- **P2-7**：`fetch` 遇 JSON/纯文本端点失败，报错建议补一句"面向 HTML 正文，JSON 请直接读响应"
- **P2-8**：fetch 正文含页脚杂质（如 runoob 备案号），可继续打磨正文选择器
- **P2-9**：无 `--lang` 时英文查询在中国网络返回中文结果；建议 SKILL.md 把
  `--lang` 提到更醒目位置，或考虑按查询语言自动选择
- **P2-10**：npx 重装覆盖旧版无提示（上游 skills CLI 行为）；建议 README 说明
  "重复 add 即更新"
- **P2-11**：README quick start 建议加一步"装完跑 doctor 验证"

## 四、亮点（保持并放大）

1. 免 key 即用，安装一条命令，更新无感
2. 中文信息源实测可达（runoob/知乎/CSDN），`--lang zh` 有效
3. `--json` 输出结构对 agent 二次处理非常友好（query/engines/results 三段）
4. doctor 输出信息密度合适，SKIP 原因明确
5. 冷却在输出中透明可见，不静默吞错
6. fetch 结构化失败（`{"ok":false}`）而非崩溃
7. 双运行时（Node/Python）行为一致性总体良好

## 五、建议修复顺序

1. P0-1（--help + flag 校验）—— 半小时工作量，收益立竿见影
2. P0-2（python bing 特征/junk 护栏）—— 影响最大，工作量中等
3. P1-5（冷却文档 + doctor 显示）—— 纯文档加一列
4. P1-3 / P1-4（输出流、引擎名提示）—— 小改动
5. P2 项按反馈排期
